Detecting Model Drift Before It Costs You: A Practical MLOps Playbook

Sai Pavan Aditya Mantripragada · April 2025 · 5 min read
MLflowSageMakerMonitoringMLOps

Production ML models have a shelf life. The world changes — user behaviour shifts, upstream data schemas evolve, the real-world distribution your model was trained on drifts away from what it sees at inference time. Without active monitoring, model quality degrades silently until someone notices in a business metric weeks later.

This post covers the practical instrumentation I use to catch drift early — statistical detectors, MLflow logging patterns, and SageMaker Model Monitor integration.

Two Kinds of Drift

First, be precise about what you are monitoring:

  • Data drift (covariate shift) — the distribution of input features P(X) changes. The model hasn't changed, but the inputs it receives differ from training data. Common cause: upstream system changes, seasonal patterns.
  • Concept drift — the relationship between inputs and outputs P(Y|X) changes. The model is still receiving similar inputs, but the correct answer has changed. Common cause: evolving user behaviour, market changes, labelling policy updates.

Data drift is detectable without labels. Concept drift requires ground truth. Design your data collection pipeline to capture delayed labels.

Statistical Tests for Data Drift

For each feature, compare the distribution of a recent window of production data against a reference (training) distribution.

from scipy import stats
import numpy as np

def detect_drift(reference: np.ndarray, production: np.ndarray,
                 alpha: float = 0.05) -> dict:
    """
    Kolmogorov-Smirnov test for continuous features.
    Chi-squared test for categorical features.
    """
    if reference.dtype in [np.float32, np.float64]:
        stat, p_value = stats.ks_2samp(reference, production)
        test = "KS"
    else:
        # Align categories
        all_cats = np.union1d(reference, production)
        ref_counts = np.array([(reference == c).sum() for c in all_cats])
        prod_counts = np.array([(production == c).sum() for c in all_cats])
        stat, p_value = stats.chisquare(prod_counts,
                                        f_exp=ref_counts * prod_counts.sum() / ref_counts.sum())
        test = "chi2"

    return {
        "test": test,
        "statistic": float(stat),
        "p_value": float(p_value),
        "drift_detected": p_value < alpha
    }

Run this for every feature in your schema. Log results to MLflow for trend tracking:

import mlflow

with mlflow.start_run(run_name="drift_check_2025_04_01"):
    for feature, result in drift_results.items():
        mlflow.log_metric(f"drift_p_{feature}", result["p_value"])
        mlflow.log_metric(f"drift_stat_{feature}", result["statistic"])
        if result["drift_detected"]:
            mlflow.set_tag(f"drift_alert_{feature}", "TRUE")

SageMaker Model Monitor

For models deployed on SageMaker, Model Monitor automates baseline capture and scheduled drift checks at the infrastructure level — no custom code needed for the monitoring job itself.

import boto3
from sagemaker.model_monitor import DataCaptureConfig, ModelMonitor

# Enable data capture on your endpoint
data_capture_config = DataCaptureConfig(
    enable_capture=True,
    sampling_percentage=20,           # capture 20% of requests
    destination_s3_uri="s3://my-bucket/capture/",
    capture_options=["REQUEST", "RESPONSE"]
)

# Create monitoring schedule (daily)
monitor = ModelMonitor(role=role)
monitor.suggest_baseline(
    baseline_dataset="s3://my-bucket/training-data/baseline.csv",
    dataset_format={"csv": {"header": True}},
    output_s3_uri="s3://my-bucket/baseline-results/"
)

monitor.create_monitoring_schedule(
    monitor_schedule_name="daily-drift-check",
    endpoint_input=endpoint_name,
    output_s3_uri="s3://my-bucket/monitoring-results/",
    statistics="s3://my-bucket/baseline-results/statistics.json",
    constraints="s3://my-bucket/baseline-results/constraints.json",
    schedule_cron_expression="cron(0 8 * * ? *)"  # daily at 8am UTC
)

Auto-Retraining Triggers

Detection is only useful if it triggers action. I use a three-tier response:

  • Alert only (p < 0.05 for ≤ 20% of features) — send Slack/PagerDuty notification, log to MLflow. Human review.
  • Shadow retrain (p < 0.01 for 20-50% of features) — automatically kick off a retraining pipeline on fresh data, run A/B test against current model. Human approves promotion.
  • Automatic rollback (performance metric drops > 10% vs baseline) — immediately roll back to previous model version while retraining runs. Zero human intervention.
# EventBridge rule triggers Lambda on Model Monitor violation
def handle_drift_alert(event, context):
    violation_count = event["detail"]["violations_count"]
    total_features = event["detail"]["total_features"]
    drift_ratio = violation_count / total_features

    if drift_ratio > 0.5:
        trigger_retraining_pipeline(auto_promote=False)
        notify_slack(f"Drift alert: {violation_count}/{total_features} features. Retraining triggered.")
    elif drift_ratio > 0.2:
        notify_slack(f"Drift warning: {violation_count}/{total_features} features.")

The Performance Baseline Problem

For concept drift, you need labels — and labels arrive late (days, weeks, sometimes months for churn prediction). Two practical approaches:

  • Proxy metrics — use click-through rate, user corrections, downstream business outcomes as real-time proxies for model quality. These arrive immediately.
  • Delayed label pipeline — architect your data platform to join prediction logs with ground truth when it arrives. Store predictions with a TTL; join on entity key when label lands in your warehouse. Feed into drift detection retroactively.
